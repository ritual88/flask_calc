# Настройка записи на встречу

Эта инструкция подключает форму сайта к Supabase и Resend. Клиент выбирает
свободное время и получает письма о заявке и её статусе, а владелец управляет
записями на сайте. Не присылай секретные ключи или пароли в чат и не сохраняй
их в Git.

## Как будет работать запись

1. Клиент указывает имя, телефон, почту и выбирает свободную дату и время.
2. Flask ещё раз проверяет слот и сохраняет запись в Supabase.
3. Ограничение в самой базе данных не даёт двум одновременным заявкам занять
   одно или пересекающееся время.
4. Клиенту приходит письмо о получении заявки, владельцу — уведомление о новой
   заявке. После подтверждения или отмены клиенту приходит ещё одно письмо.
5. Владелец входит на сайт и подтверждает, отменяет, удаляет запись или
   повторяет неудачную отправку письма.

Расписание фиксировано: понедельник–пятница, 10:00–18:00 по Москве; встреча
длится 60 минут, начала предлагаются с шагом 30 минут. Запись резервирует время
сразу, даже пока ждёт подтверждения. Отмена и удаление освобождают его.

## Шаг 1. Обновить таблицу Supabase

Этот SQL подходит как для пустой новой таблицы, так и для прежней таблицы
`appointments`. Он добавляет почту, время начала/окончания, статусы писем и
защиту от пересекающихся заявок.

1. Открой нужный проект в [Supabase](https://supabase.com/dashboard).
2. Открой **SQL Editor** и создай новый запрос.
3. В VS Code открой `database/appointments.sql`, скопируй весь файл в запрос и
   нажми **Run**.
4. Убедись, что SQL завершился без ошибки.

Если скрипт сообщает о пересекающихся активных заявках, сначала в **Table
Editor → appointments** найди старые заявки со статусом `pending` или
`confirmed`, которые занимают одно и то же время. Отмени одну из них, изменив
её статус на `declined` (это значение допускает старая схема), затем выполни
SQL ещё раз: скрипт преобразует `declined` в `cancelled`. Не удаляй реальные данные,
если не уверен, что они больше не нужны.

Проверка результата: в `appointments` появились столбцы `email`, `starts_at`,
`ends_at`, `client_email_status` и `owner_email_status`. Обычные посетители
не могут читать таблицу напрямую; доступ получает только серверный Flask.

## Шаг 2. Получить ключ Resend для теста

Здесь нужно сделать только одно действие в Resend — создать API-ключ.
`onboarding@resend.dev` вводить в Resend не нужно: это готовый тестовый адрес
отправителя, который сайт укажет в настройке Render.

1. Создай аккаунт на [Resend](https://resend.com/) и открой **API Keys**.
2. Нажми **Create API Key**, создай ключ и скопируй его. На следующем шаге
   вставь его в Render как значение переменной `RESEND_API_KEY`.
3. Когда будешь заполнять настройки Render, введи:
   - **Key:** `EMAIL_FROM`
   - **Value:** `onboarding@resend.dev`
4. Оставь `EMAIL_TEST_MODE=true`. В этом режиме сайт отправляет тестовые
   сообщения только на адрес Resend `delivered@resend.dev`, а не клиентам,
   владельцу или в обычный почтовый ящик. Проверить результат можно в панели
   Resend.

Иными словами, `onboarding@resend.dev` — это имя отправителя для теста, а не
почтовый ящик, который нужно открыть. Подтверждать свой домен на этом этапе
не нужно.

Чтобы отправлять письма клиентам и владельцу по-настоящему, сначала добавь и
подтверди свой домен отправителя в Resend. Затем укажи адрес с этого домена в
`EMAIL_FROM` и измени `EMAIL_TEST_MODE` на `false`. Пока тестируешь, оставляй
`EMAIL_TEST_MODE=true`: адреса клиентов и владельца не получат письма.

## Шаг 3. Добавить настройки в Render

1. Открой [Render Dashboard](https://dashboard.render.com/), выбери сервис
   `flask-calc-7xeh` и открой **Environment**.
2. В **Environment Variables** добавь перечисленные ниже пары **Key** и
   **Value**. Названия Key нужно написать точно; в Value вводится своё значение.

| Key | Что вставить в Value |
|---|---|
| `SUPABASE_URL` | **Project URL** из того же проекта Supabase, где выполнил SQL |
| `SUPABASE_SERVICE_ROLE_KEY` | Секретный `service_role` ключ из **Supabase → Settings → API Keys** |
| `OWNER_PASSWORD` | Придуманный пароль владельца, не короче 16 символов |
| `FLASK_SECRET_KEY` | Случайная строка не короче 32 символов |
| `RESEND_API_KEY` | API key, который создал на предыдущем шаге |
| `EMAIL_FROM` | Для теста: `onboarding@resend.dev` |
| `OWNER_EMAIL` | Почта владельца, куда должны приходить уведомления |
| `EMAIL_TEST_MODE` | Для безопасного теста — `true` |

`SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` должны принадлежать одному проекту.
Не используй `anon`/`publishable` ключ: серверу нужен секретный `service_role`.
Он даёт широкий доступ к базе, поэтому храни его только в Render Environment.

Для создания случайного `FLASK_SECRET_KEY` выполни на своём компьютере:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Скопируй результат прямо в Value для `FLASK_SECRET_KEY`. Не меняй ключ при
каждом запуске: иначе вход владельца будет сбрасываться. Настоящие значения не
добавляй в `.env.example`, Python, HTML, JavaScript, GitHub или чат.

Нажми **Save Changes** и дождись, пока сервис перезапустится. В разделе **Events**
или **Logs** дождись статуса **Live**.

## Шаг 4. Опубликовать код и проверить

В Render должен быть опубликован новый код из GitHub. Перед отправкой изменений
в Git проверь список файлов и убедись, что в нём нет настоящего `.env` или
секретов. После deploy:

1. Открой публичный сайт, выбери будний день в следующие 30 дней и проверь,
   что появились свободные слоты по Москве.
2. Отправь тестовую заявку, используя тестовые контактные данные. Заявка должна
   сохраниться, а сайт — подтвердить её отправку.
3. Открой ссылку **Вход владельца** внизу сайта, введи `OWNER_PASSWORD` и
   проверь карточку заявки.
4. В Resend проверь события отправки тестовых писем.
5. В кабинете нажми **Подтвердить**: статус изменится, клиентское письмо
   появится в Resend. После этого проверь отмену и повторную запись на
   освободившийся слот.
6. Проверь кнопку **Удалить навсегда** только на тестовой заявке: удалённая
   строка не восстанавливается.

Если письмо не отправилось, заявка не теряется: в кабинете виден статус
«Ошибка отправки» и появляется кнопка **Повторить отправку писем**. Проверь
настройки Resend, затем повтори отправку. В тестовом режиме успешные письма
видны в Resend, но не попадают в обычный почтовый ящик.

## Если что-то пошло не так

- **SQL сообщает о пересечениях:** проверь старые активные записи и отмени
  дубликаты перед повторным запуском скрипта.
- **Нет свободных слотов:** выбери будний день в следующие 30 дней. Уже
  зарезервированное время скрыто; встречи длятся час.
- **Заявка не сохраняется:** проверь Supabase URL, `service_role` ключ и то,
  что SQL выполнен именно в этом проекте.
- **Письма отмечены ошибкой:** проверь `RESEND_API_KEY`, `EMAIL_FROM` и
  `EMAIL_TEST_MODE`; в тестовом режиме используй `onboarding@resend.dev`.
- **Владелец не может войти:** проверь, что `OWNER_PASSWORD` не короче
  16 символов и Render завершил перезапуск после сохранения переменных.

Автоматические тесты запускаются в терминале проекта:

```powershell
python -m unittest discover -s tests -v
```

Тесты подменяют обращения к Supabase и Resend, поэтому не создают реальных
записей и не отправляют реальные письма.
